          What the broker decided

            The rules of the broker

            The simulator uses the code of @headroom/core, the same code as the daemon. Each reason in the queue comes from the broker itself.

            The room of each resource

            The memory is measured. A new lease gets the free memory, less 1 GB for the system, less the part of each lease that its job does not use yet.

            The processors are counted. The leases do not take the last 2 cores, so the person at the computer keeps them.

            The order of the queue

            A higher priority goes first. A waiting lease gains 1 of priority for each minute in the queue.

            After 10 minutes, no smaller request goes before the first lease in the queue.

            A lease that cannot fit at any time

            A lease that asks for more than the capacity less the reserve cannot start at any time. The broker cancels it at once, with the reason.

            Spawn-heavy jobs and browser tests

            A burst of process starts can stop the start of a browser. A job is spawn-heavy when its past runs started more than 600 processes in one minute.

            A spawn-heavy job and a browser test do not run at the same time.

            The sum of the start rates

            Several moderate jobs together also make a burst. Beside a browser test, the other leases together start at most 600 processes in one minute.

            The memory limit

            With --limit, the job cannot commit more memory than its lease. A job that grows past its lease stops, and the other jobs keep their memory.

            Without the limit, the lease is advisory. Turn the switch off and add the job with a leak to see the difference.

            Why

            Many coding sessions, Docker and the browser share one computer. When the memory gets low, each session gets slow, and jobs stop. Before headroom, a person looked at the free memory and told each session when to start a heavy run. That is slow, and it does not scale.

            headroom does three jobs:

            1. Observe. It samples the memory of the computer every few seconds, and gives the memory of each process tree to its owner.
            2. Admit. A job asks for a lease of memory, processors or a slot. The job starts when the lease fits. Otherwise it waits in the queue.
            3. Enforce. headroom starts the job with a memory limit at the size of its lease. A job that grows past its lease stops with a clear reason.

            Use

            Install the daemon as a service of your user. It starts at login, and it listens on 127.0.0.1:4730.

            headroom service install
headroom service status

            Run a heavy job under a lease. The job waits until the memory is free.

            headroom run --mem 2g -- pnpm test
headroom run --mem 1g --cpu 4 --limit -- pnpm build
headroom run --slot docker --mem 1g -- docker compose up -d

            See the memory, the free amounts, the leases and the memory of each owner:

            headroom status

            Status

            Version 0 works: the sampler, the leases, the daemon, the command line and the service. The memory limit is on Windows, with a job object. Linux has no limit yet.

            The Status page gives the plan and the state of each item. The README gives the full manual.
